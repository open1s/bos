# TS-03 Generic Query Evidence & Bounded Retrieval

Status: Proposed
Scope: `crates/codintelli`
Prerequisites: TS-01 Native ParsedDocument and TS-02 Query Registry/Execution
Architecture constraint: Tree-sitter native syntax is the only syntax-tree representation

## 1. Purpose

TS-03 defines the smallest generic contract that allows codintelli consumers to use Tree-sitter query results for code navigation and bounded agent context retrieval.

TS-03 does not build a semantic compiler, language-specific AST, graph database, vector database, or LLM-powered retrieval system. It connects native syntax queries to source-grounded, uncertainty-aware evidence and retrieval.

The central output is **evidence**, not a reconstructed syntax model:

- where the evidence came from;
- which source snapshot and parser/query definitions produced it;
- which Tree-sitter query/capture identified it;
- whether extraction was complete or partial;
- how much source/context may safely be returned.

## 2. Non-goals

TS-03 MUST NOT:

- define Rust-specific `Module`, `Import`, `Symbol`, namespace, scope-tree, or declaration DTOs;
- serialize Tree-sitter `Tree`, `Node`, or cursor internals;
- claim compiler-resolved references from syntax-only matches;
- require LSP, SCIP, compiler execution, build scripts, Cargo metadata execution, LLMs, graph databases, vector databases, or external services;
- persist every query result by default;
- return unbounded source text or whole-file context as a convenience fallback;
- treat a single same-name candidate as a resolved semantic edge.

## 3. Normative design constraints

### 3.1 Native Tree-sitter ownership

The parser's `ParsedDocument` continues to own the source snapshot and native Tree-sitter `Tree`. Query execution operates on that tree.

TS-03 may retain generic evidence metadata and source ranges. It MUST NOT copy grammar structure into another tree or persist standalone `Node` values.

### 3.2 Evidence is source-bound

Every evidence item MUST identify:

- host-supplied `WorkspaceId`;
- normalized workspace-relative path;
- source fingerprint for the exact immutable bytes parsed;
- language ID;
- provider ID and provider version;
- query ID and query version;
- capture name/index and byte range;
- parse coverage and query execution coverage.

A source fingerprint MUST be computed over the exact source bytes, using a documented stable algorithm and explicit algorithm/version tag. It MUST NOT be inferred from modification time, file size, or path alone.

Workspace identity is supplied by the host. codintelli MUST NOT derive WorkspaceId from a path, Git remote, repository name, or branch.

### 3.3 Evidence is not semantic resolution

A query capture proves only that a grammar pattern matched a source range in a particular parse snapshot.

Candidate relationships MUST preserve provenance and uncertainty. At minimum, distinguish:

- no candidate;
- one candidate;
- multiple candidates;
- unsupported/insufficient evidence;
- stale evidence;
- incomplete coverage.

A unique candidate MUST NOT be promoted to compiler-resolved semantics merely because it is unique.

### 3.4 Coverage is first-class

A retrieval result MUST report whether it is complete for the requested scope. It must distinguish at least:

- complete;
- partial due to unsupported language/provider;
- partial due to recovered parse;
- partial due to query output limit;
- partial due to match limit;
- cancelled;
- deadline/budget exhausted;
- stale index/source snapshot;
- I/O or parse failure.

Do not collapse these states into an empty result or a successful result with omitted diagnostics.

## 4. Requirements

### REQ-TS-08 — Query definition identity and invalidation

Query definitions are versioned by stable query ID and explicit query version. Evidence generated by a different query version or provider/grammar version is stale for that query.

Acceptance:
- [ ] Evidence records the query ID and query version.
- [ ] Provider ID/version and language are included in the compatibility identity.
- [ ] A query version change invalidates only evidence produced by that query definition.
- [ ] A provider/grammar version change invalidates evidence produced by the incompatible provider version.
- [ ] Invalidation does not silently relabel old evidence as current.
- [ ] Query source is not required to be persisted; identity/version is sufficient to detect incompatibility.

### REQ-TS-09 — Query and parse coverage propagation

Coverage must flow from parsing and query execution into every evidence batch and retrieval response.

Acceptance:
- [ ] Recovered parse status is retained.
- [ ] Query output-limit and match-limit states remain distinguishable.
- [ ] Cancellation and deadline are not reported as complete.
- [ ] Unsupported files/providers are represented in scope coverage, not silently omitted.
- [ ] Empty results distinguish complete-no-match from incomplete-no-match.
- [ ] Aggregation across files preserves the worst relevant coverage and per-file diagnostics.

### REQ-TS-10 — Source snapshot identity and provenance

Evidence must be verifiably tied to the exact source snapshot used for parsing.

Acceptance:
- [ ] Fingerprint algorithm and version are explicit.
- [ ] Fingerprint is computed from exact source bytes.
- [ ] Evidence includes WorkspaceId, relative path, fingerprint, provider identity, query identity, capture identity, and byte range.
- [ ] Source changes make prior evidence stale even when path and file size remain unchanged.
- [ ] Cross-workspace evidence cannot be reused without an explicit host-level mapping.
- [ ] Byte ranges are validated against the matching source snapshot before text is returned.

### REQ-TS-11 — Deterministic evidence ordering

For identical source bytes, grammar/provider version, query definition/version, and execution configuration, evidence ordering must be stable.

Acceptance:
- [ ] Ordering contract is documented (file path, query identity, match/capture source order).
- [ ] HashMap iteration order does not leak into public result ordering.
- [ ] Repeated runs produce byte-for-byte equivalent serialized generic evidence, excluding explicitly nondeterministic diagnostics.
- [ ] Tests cover multiple matches with overlapping and nested captures.
- [ ] Determinism does not depend on thread scheduling.

### REQ-TS-12 — Incremental invalidation contract

TS-03 defines invalidation boundaries; it does not require a persistent database or filesystem watcher.

Acceptance:
- [ ] A changed source fingerprint invalidates evidence for that file.
- [ ] A removed file invalidates its evidence.
- [ ] A query-version change invalidates evidence for that query only.
- [ ] A provider/grammar-version change invalidates evidence produced by that provider version.
- [ ] Unchanged compatible evidence can be reused.
- [ ] Failed re-indexing preserves last-known-good evidence but marks it stale relative to the current source.
- [ ] Rebuild and update operations publish a consistent snapshot rather than partially mutating visible results.

### REQ-TS-13 — Retrieval budget and bounded context

Retrieval must be bounded independently of index size and query execution output limits.

Acceptance:
- [ ] Caller supplies explicit limits for evidence count, total returned source bytes, per-snippet bytes, and files visited.
- [ ] Limits are validated against documented hard ceilings.
- [ ] Truncation is explicit and reports which budget was reached.
- [ ] Returned snippets are source slices from the fingerprint-matched snapshot.
- [ ] No silent fallback to whole-file content is allowed.
- [ ] Retrieval preserves source path, byte range, and evidence provenance.
- [ ] Deterministic ranking/tie-breaking is documented; ranking must not imply semantic certainty.

### REQ-TS-14 — Generic evidence contract

The owned evidence representation must remain language-neutral and must not mirror grammar nodes.

Acceptance:
- [ ] Evidence uses generic query/capture identity and source ranges.
- [ ] No Rust-specific syntax enum or language-specific structural DTO is introduced.
- [ ] No Tree-sitter Node/Tree is serialized or persisted.
- [ ] Evidence can refer to multiple languages using LanguageId/provider metadata.
- [ ] Language-specific interpretation remains in provider query definitions or adapters, not in the shared evidence schema.
- [ ] Any relationship/candidate record carries provenance and an explicit confidence/uncertainty state.

### REQ-TS-15 — Persistence is opt-in and use-case driven

TS-03 defines an in-memory evidence contract first. Persistence is a separate decision based on measured retrieval and restart requirements.

Acceptance:
- [ ] No database dependency is introduced by TS-03.
- [ ] Persistence format is not selected before access patterns, volume, and crash-recovery requirements are measured.
- [ ] If persistence is later proposed, it stores generic evidence and fingerprints only, never native Node/Tree objects.
- [ ] Schema and query-version migrations are explicit.
- [ ] Interrupted writes cannot publish a mixed index generation.
- [ ] A rebuild path exists from bounded source files and registered query definitions.

## 5. Proposed generic data contract

This section is conceptual and does not mandate final Rust struct names or prematurely freeze serialization.

A generic evidence item needs these fields or equivalent validated accessors:

| Field | Meaning |
|---|---|
| workspace identity | Host-supplied checkout/worktree identity |
| relative path | Normalized path within that workspace |
| source fingerprint | Algorithm/version plus digest of exact bytes |
| language/provider | Language ID, provider ID, provider version |
| query identity | Query ID and query version |
| capture identity | Capture index and stable capture name |
| source location | Half-open byte range in the fingerprinted source |
| coverage | Parse coverage and query execution coverage |

An evidence batch additionally needs deterministic ordering and diagnostics. A retrieval result additionally needs the requested scope, returned snippets/evidence, truncation reason, and aggregate coverage.

Do not add a generic `NodeRecord`, `AstNode`, `DeclarationTree`, or other node-shaped DTO as an indirect AST.

## 6. Retrieval behavior

The initial retrieval API should be narrow and deterministic:

1. Accept a host-supplied workspace identity and an explicit file/query scope.
2. Validate that evidence matches the current source fingerprint and query/provider versions.
3. Select evidence using stable ordering and documented ranking.
4. Resolve requested byte ranges against the exact source snapshot.
5. Return only bounded source snippets with provenance.
6. Report truncation and incomplete coverage explicitly.

Retrieval MUST NOT infer symbol identity from capture names alone. Query captures can guide navigation and snippet selection; semantic resolution remains a separate capability requiring stronger evidence.

## 7. Incremental update model

TS-03 specifies logical invalidation, not a watcher implementation.

The minimum update unit is one source file/query-definition pair. A source change invalidates evidence for that file. A query definition change invalidates evidence for that query. A provider/grammar change invalidates evidence for the incompatible provider version.

Updates should be prepared off to the side and published atomically at an index-generation boundary. If parsing or query execution fails, retain the previous generation as last-known-good but mark it stale for the changed input. Never mix new source fingerprints with old evidence and report the result as current.

## 8. Security and resource boundaries

- Evidence and retrieval operate only on source bytes already read through `WorkspaceFs`.
- No filesystem path from query text or capture names is interpreted as a path.
- Source ranges are checked against the matching fingerprinted snapshot.
- All output budgets have hard ceilings and overflow-safe accounting.
- Query execution limits and retrieval output limits are independent.
- No project code, build script, package manager, compiler, or test command is executed.
- No hard RSS/CPU isolation claim is made for in-process Tree-sitter. Such isolation, if required, is a separate process/OS boundary design.

## 9. Test strategy

- Fingerprint changes when one source byte changes, including same-length edits.
- Evidence from another WorkspaceId is rejected.
- Evidence from stale source/query/provider versions is not returned as current.
- Empty-complete and empty-incomplete results are distinguishable.
- Recovered parse and query-limit coverage propagate to retrieval.
- Deterministic ordering holds across repeated runs and parallel file completion order.
- Every retrieval budget is tested at boundary, over boundary, and with `usize::MAX`.
- Returned snippets never exceed per-snippet or aggregate byte budgets.
- Invalid ranges and mismatched fingerprints are rejected.
- Incremental update failure preserves last-known-good generation and marks it stale.
- No tests require LLMs, network access, compilers, or executing workspace code.

## 10. Implementation slices

| Slice | Scope | Expected size |
|---|---|---|
| TS-03A | Generic evidence contract + source fingerprint primitive | <= 3 work days |
| TS-03B | Coverage propagation and deterministic evidence batches | <= 3 work days |
| TS-03C | Bounded source-snippet retrieval | <= 3 work days |
| TS-03D | Query/source/provider invalidation contract | <= 3 work days |
| TS-03E | Atomic in-memory index generation/update behavior | <= 3 work days |

Each slice must have independent tests and a reviewable API. Persistence, watcher integration, semantic resolution, and runtime adapters remain outside these slices unless separately justified.

## 11. Definition of done

TS-03 is complete when generic evidence is source-bound, coverage-aware, deterministic, and bounded; retrieval returns only fingerprint-validated source snippets; invalidation is explicit; and all acceptance tests pass under the declared MSRV and core workspace CI.

The implementation must continue to use native Tree-sitter syntax and must not introduce a parallel AST or language-specific syntax DTOs.
